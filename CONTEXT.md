# CONTEXT.md — Domain Glossary

This file names the domain concepts in trading-analyst so that discussions,
code reviews, and architecture work use consistent vocabulary. Terms here are
verified against the code (schema, types, package entry points), not inferred
from prose docs — those (`README.md`, `architecture.md`, `sprints.md`) lag
behind the implementation in places; this file is the source of truth for
naming.

Each entry: definition, key attributes, relations, and where it lives in code.

## Core entities

### User
A person using the app. Owns watchlists, positions, alerts, and AI spend.
Role is `admin` or `member`.
- Key fields: `id` (uuid), `email`, `passwordHash`, `role`, `telegramChatId`
- Relations: has many ApiToken, WatchlistAsset, Position, Alert, AiCostLedger entries
- `packages/db/src/schema/index.ts` (table `users`), `packages/shared-types/src/user.ts`

### ApiToken
Programmatic auth credential for a User, independent of session login.
- Key fields: `userId` (FK), `tokenHash` (never plaintext), `revokedAt`
- `packages/db/src/schema/index.ts` (table `api_tokens`)

### WatchlistAsset
An asset a User is tracking; determines which assets enter the analysis
pipeline (market data → indicators → signal → AI).
- Key fields: `userId`, `assetId`, `symbol`, `coingeckoCoinId`, `asset` (jsonb Asset snapshot), `aiEnabled`, `source` (`seed` | `manual` | `position`)
- Capped at `MAX_WATCHLIST_ASSETS = 10` per user (`packages/shared-types/src/watchlist.ts`)
- `packages/db/src/schema/index.ts` (table `watchlist_assets`)

### Asset
Not a table — a Zod-only value type (`packages/shared-types/src/asset.ts`)
describing the traded instrument (symbol, asset class, exchange, metadata).
Carried by value through the whole pipeline (embedded in WatchlistAsset,
MarketSnapshot, IndicatorSnapshot, SignalAggregationSnapshot, AssetAnalysis).

### MarketSnapshot
Latest price/candle data for one asset+timeframe from one market-data
provider. Upsert-only — no historical time series is kept in this table.
- Key fields: `assetId`, `provider`, `timeframe`, `candle`, `candles` (series), `priceChangePercent`
- `packages/db/src/schema/index.ts` (table `market_latest_snapshots`)

### IndicatorSnapshot
Technical-indicator computation (moving averages, oscillators, volatility,
support/resistance levels, market structure) derived from one MarketSnapshot.
- Key fields: `movingAverages`, `oscillators`, `volatility`, `levels`, `structure`
- `packages/db/src/schema/index.ts` (table `indicator_latest_snapshots`)

### SignalAggregationSnapshot
Deterministic, rule-based fusion of MarketSnapshot + IndicatorSnapshot (plus
optional market context and active Position) into a single trading signal —
computed *before* any AI call. This is the "translate raw data into a
signal" layer.
- Key fields: `signalStrengthScore` (0–100, sum of label contributions), `bias`, `regime`, `riskFlags`, `keyLevels`, `labels`, `snapshotHash` (change-detection hash)
- `packages/db/src/schema/index.ts` (table `signal_aggregation_latest_snapshots`)
- Built by `packages/signal-aggregation/src/snapshot.ts`

### AssetAnalysis / LatestAssetAnalysis
The AI's decision for an asset: trading state, suggestion, and a decision
card (summary, reasons, action plan, invalidation). This is "the AI
decision" referenced throughout the codebase and docs.
- **Naming note:** two Zod schemas exist — `assetAnalysisSchema` (carries `userId`) and `latestAssetAnalysisSchema` (no `userId`). The table `asset_analysis_latest_snapshots` maps to `LatestAssetAnalysis` — that's the one actually persisted and read by the worker. Prefer this name in new code and docs.
- Key fields: `state` (AssetState: `IGNORE`/`WATCH`/`PREPARE`/`ACTIONABLE`/`IN_POSITION`/`EXIT_WARNING`/`INVALID`), `suggestion`, `decisionCard`, `aiConfidence` (clamped to `signalStrengthScore ± 20`), `modelUsed`, `promptVersion`, `snapshotHash`, `costEstimateUsd`
- `packages/db/src/schema/index.ts` (table `asset_analysis_latest_snapshots`), `packages/shared-types/src/analysis.ts`
- Produced by `packages/ai-analysis` from one SignalAggregationSnapshot

### Alert
A notification sent to a User when an asset's (or position's) analysis state
changes — e.g. `WATCH` → `ACTIONABLE`. Delivered via dashboard/Telegram/WhatsApp.
- Key fields: `kind` (`market`|`position`), `severity`, `status` (`suggested`→`delivered`→`acknowledged`/`ignored`/`expired`), `channels`, `dedupeKey` (prevents duplicate alerts for the same transition), `previousState`/`currentState`
- `packages/db/src/schema/index.ts` (table `alerts`)
- Generated by `packages/alert-engine` (pure function, no I/O); delivered by `packages/chat-layer`

### Position
A User's real (not hypothetical) trade on an asset — entry price, quantity,
realized/unrealized PnL, stop loss.
- Key fields: `direction` (`long`|`short`), `status` (`open`|`partially_closed`|`closed`), `averageEntryPrice`, `remainingQuantity`, `realizedPnl`/`unrealizedPnl`, `stopLoss`
- `packages/db/src/schema/index.ts` (table `positions`)
- An active Position can influence SignalAggregationSnapshot/AssetAnalysis (position-aware analysis)

### AnalysisOutcome
Self-scoring record: was the AI's prediction correct? Created as `pending`
when an AssetAnalysis is generated, evaluated later (default 24h) against
actual price movement.
- Key fields: `status` (`pending`→`evaluated`|`skipped`), `evaluateAfter`, `directionCorrect`, `invalidationHit`
- `packages/db/src/schema/index.ts` (table `analysis_outcomes`)
- Built/evaluated in `apps/worker/src/outcomes.ts`

### ServiceHeartbeat
Operational health status of an external provider or internal cost-cap
check (e.g. `provider:coingecko`, `ai:daily-cost-cap`). Operational
observability, not trading domain.
- `packages/db/src/schema/index.ts` (table `service_heartbeats`)

### AiCostLedger
Per-user ledger of AI (OpenAI) spend, used to enforce `MAX_DAILY_AI_COST_USD`.
- `packages/db/src/schema/index.ts` (table `ai_cost_ledger`)

## Package responsibilities (the seams)

Dependency flow is one-directional, raw data → action, orchestrated entirely
by `apps/worker`:

```
market-data ──┐
              ├─► signal-aggregation ─► ai-analysis ─► alert-engine ─► chat-layer
indicators ───┘                              │
                                              ▼
                                    outcomes (worker-local, no package)

db  ◄── imported ONLY by apps/worker — no packages/* domain package touches it directly
```

- **`packages/market-data`** — fetches raw market data (CoinGecko candles, Bybit funding/OI, Fear & Greed index) and shapes it into validated `MarketSnapshot`. No DB, no AI.
- **`packages/indicators`** — pure technical-indicator math from a candle series → `IndicatorSnapshot`. No I/O.
- **`packages/signal-aggregation`** — fuses market + indicator (+ context + position) into `SignalAggregationSnapshot`. Rule-based scoring, no AI, no DB.
- **`packages/ai-analysis`** — turns a `SignalAggregationSnapshot` into a `LatestAssetAnalysis` via an LLM provider (OpenAI). Does not persist — returns the result to its caller.
- **`packages/alert-engine`** — pure function comparing two `LatestAssetAnalysis` snapshots to decide whether an `Alert` is warranted. No delivery, no DB.
- **`packages/chat-layer`** — outbound delivery adapters (Telegram, Twilio/WhatsApp) and inbound command parsing. Pure I/O adapter.
- **`packages/db`** — Drizzle schema + one CRUD module per aggregate. The *only* consumer is `apps/worker`.
- **`packages/shared-types`** — the vertical seam: Zod schemas every other package depends on, so domain packages stay decoupled from each other while remaining type-compatible.
- **`apps/worker`** — the sole orchestrator. `pipeline.ts` (`runAnalysisCycle`) sequences every step above and is the only place that knows the full order and the only consumer of `db`.

## Known architectural rough edges (context for future refactors)

- **ID type inconsistency**: `users`, `apiTokens`, `watchlistAssets` use `uuid`; `positions`, `alerts`, `analysisOutcomes`, and the `*_latest_snapshots` tables use `text` custom IDs. `userId` on `positions`/`alerts` is plain `text` with no FK constraint (unlike `apiTokens`/`watchlistAssets`/`aiCostLedger`, which do have `.references()`).
- **Duplicated orchestration logic**: `generateLatestAssetAnalysis` and `generateAssetAnalysisFromSignalSnapshot` in `apps/worker/src/analysis.ts` have nearly identical bodies (one fetches its own snapshot, the other receives it directly) — candidate for consolidation.
- **Manual DI pattern**: worker orchestration functions (`ingestLatestMarketData`, `generateLatestAssetAnalysis`, `processOutcomeEvaluationJob`, etc.) accept optional override parameters for every package/db function they call (e.g. `saveHeartbeat`, `getActivePositionForAssetFn`, `recordAiCostFn`) — this is the explicit seam surface for testing; keep it consistent when adding new orchestration steps.
- **"Latest" tables are not history**: `market_latest_snapshots`, `indicator_latest_snapshots`, `signal_aggregation_latest_snapshots`, `asset_analysis_latest_snapshots` each hold exactly one row per asset+timeframe (upsert). `analysis_outcomes` is the only place with an append-only historical record.
